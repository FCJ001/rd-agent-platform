# 研发/质量域 · 生产级演进方案

> 场景定位：**研发/质量域的问题单闭环**。不是售后维修，不是功能安全域。
> 交付定位：**练手 + 面试展示**，但按生产规范分层，规模缩小。
>
> 目标一句话：把「只能聊天」升级为「**能落单、能被采纳、能收敛**」的问题单闭环。

## 1. 目标架构

核心变化：**取消 bypass，改成一张图、Supervisor 每轮都在场**。

```
┌─────────────────────────────────────────────────────────────┐
│                     Chat Router (只做会话/鉴权)               │
└───────────────────────────┬─────────────────────────────────┘
                            │  每一轮都进图
                            ▼
┌─────────────────────────────────────────────────────────────┐
│              Supervisor Graph (LangGraph, 带 checkpointer)    │
│                                                              │
│   ┌──────────────┐                                          │
│   │ 入口: router │  ← 确定性前置路由(正则/关键词) → 命中直接走 │
│   └──────┬───────┘    未命中才问 LLM(便宜模型)               │
│          │                                                   │
│          ▼                                                   │
│   ┌──────────────────────┐   图状态关键字段:                  │
│   │  Supervisor Node     │   · active_task: str|None        │
│   │  (每轮都在场)         │   · task_state: dict             │
│   │                      │   · current_issue_id: int|None   │
│   │  看 active_task:      │                                  │
│   │  · None  → 意图路由   │                                  │
│   │  · 有值  → 先过打断器  │  ← 【逃生口】在这一层            │
│   └──────┬───────────────┘                                  │
│          │                                                   │
│          ▼                                                   │
│   ┌──────────────────────┐                                  │
│   │ Triage Subgraph      │  作为【子图节点】内建,不是 tool   │
│   │ (保留现有 10 节点拓扑) │  interrupt() 实现可打断            │
│   └──────────────────────┘                                  │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│  Issue Closed Loop 闭环层                                    │
│  issue_draft → 人工确认 → ALM 建单 → 结论回写 → 采纳/否决    │
│                                       └→ 反馈回流图谱/权重    │
└─────────────────────────────────────────────────────────────┘
```

**为什么这么改（面试核心论述）**：

现在的写法是 **agent-as-tool** 模式（`call_triage_agent` 是个 `@tool`）。这个模式的前提是**工具单轮无状态**——一问一答，控制权立刻还给 Supervisor。但 triage 是多轮有状态的，套这个模式必然别扭，所以才要在外面打 Redis 标记 bypass，结果状态脱离 Supervisor 视野，切不出去。

生产上的两种主流解法：

- **单图 + Supervisor 每轮都跑**（LangGraph 系主流）：活跃任务变成图状态字段，Supervisor 每轮有权力决定"继续还是切换"。**本方案选这个。**
- **Handoff 交接棒**（OpenAI Agents SDK / AutoGen 系）：子 agent 用 `transfer_to_xxx()` 主动交出控制权，逃生口天然内建。

选第一个的理由：改动是**渐进式的**，现有 triage 图可以原样作为子图挂进来，不用重写成 agent 间通信。

## 2. 状态与上下文管理

### 2.1 单一状态源

| 现在 | 改成 |
|---|---|
| `triage_state:{u}:{s}` (Redis 裸 JSON) | 全部进 LangGraph checkpointer |
| `triage_active:{u}:{s}` (旁路标记) | 图状态字段 `active_task` |
| Supervisor checkpointer（另一套） | 同一个 checkpointer，同一 thread_id |

**关键点**：`thread_id` 统一为 `{user_id}:{session_id}`，全链路只有一个。这样 Supervisor 能看到分诊结论——现在两套 checkpointer 是分离的，导致分诊收敛后用户回"创建"，Supervisor 是在**不知道结论是什么**的情况下收到一个孤零零的"创建"。

### 2.2 会话级 vs 用户级记忆分层

```
thread_id = {user_id}:{session_id}     ← 会话内：对话历史、活跃任务、当前问题单
   ↓ 收敛后下沉
namespace = ("users", user_id, "issues")   ← 用户级：历史问题单、已确认结论
   ↓ 脱敏后跨用户
namespace = ("knowledge", "fault_cases")   ← 知识级：可复用的故障案例
```

现有 `MilvusStore` 的 `namespace=("users", user_id, "memories")` 是用户级的，这个分层可以沿用，**关键是要说清楚"什么进哪一层"**：

- **不能跨用户的**：VIN、车牌、车主联系方式、原始报障语音
- **可以跨用户的**：脱敏后的「现象组合 → 根因 → 修复方案」三元组

### 2.3 摘要与长会话

`SummarizationMiddleware(trigger=[("tokens", 4000), ("messages", 6)], keep=("messages", 6))` 现在挂在 Supervisor 上。改成单图后要注意：

- 摘要中间件**只作用于对话消息**，不能把结构化状态（`confirmed_phenomena`、`candidate_causes`）也摘掉
- 研发场景的对话可能很长（工程师会贴一大段日志），建议触发阈值按 token 而非消息数（现在两个都有，可以保留）
- **工程日志要做预压缩**：贴进来的 DTC 扫描报告可能有几千行，应该在进图**之前**用 `report/parser.py` 抽成结构化字段，而不是让 LLM 读全文

## 3. 分诊内核增强

保留现有 10 节点拓扑（`dispatcher` 那个空节点入口可以顺手改用 `set_conditional_entry_point` 消掉，langgraph 1.1.6 支持，已实测等效）。要增强的是内核质量。

### 3.1 ★ 置信度：从"拍数字"改成"证据驱动"

**这是最能体现生产级的一个改动。**

现状 `confidence.py` 的问题：

```python
base_confidence = 命中现象数 / 该根因总现象数   # 位置基，没考虑现象的重要性差异
score += 0.15   # is_core 命中（为什么是 0.15？）
score += 0.15   # DTC 匹配（和现象权重一样重？）
score -= 0.20   # 核心现象被否认（不对称，为什么减得比加得多？）
```

这些常数没有来源，也没法解释。而且**最致命的是：用户回一句"好像是"和回一句"确定，我拿诊断仪读过就是这个码"，对置信度的影响完全一样**。

**改法：引入证据等级（Evidence Tier）**

```python
class EvidenceTier(str, Enum):
    DTC_CONFIRMED   = "dtc"      # 诊断仪读出的 DTC —— 客观证据，权重 1.0
    MEASURED        = "measured" # 实测数据（电压、阻值、日志时间戳）—— 0.9
    OBSERVED        = "observed" # 用户可感知现象（黑屏、异响）—— 0.7
    REPORTED        = "reported" # 用户转述他人（"4S店说..."）—— 0.4
    INFERRED        = "inferred" # LLM 推断 —— 0.2
```

**证据融合用 Noisy-OR**（独立证据叠加，不会像加法那样超过 1）：

```
P(cause | e1..en) = 1 - Π(1 - w_i × p_i)
```

其中 `w_i` 是证据等级权重，`p_i` 是现象→根因的关联强度（来自 `CausePhenomenon.weight`）。

**加成贝叶斯先验**（研发场景很实用）：

```
prior = 该根因的历史命中率（来自 feedback_loop 的采纳记录）
      × 时效衰减（半衰期 180 天：老问题是老车型的，新批次可能已修复）
      × 平台系数（同平台车型的故障可迁移，跨平台打折）
      × 批次系数（同批次车辆故障高度相关）
```

**为什么这套在面试里好讲**：每一分置信度都能回答"**为什么是这个数**"——

> "这条 DTC 是诊断仪读出来的客观证据，权重 1.0；现象是用户口述的，权重 0.7；两者独立，用 Noisy-OR 融合得到 0.82。再乘上该根因在本车型平台的历史命中率 0.3 和 180 天时效，最终 0.68，超过 0.65 收敛阈值。"

生产上还要**可解释输出**：结论里带上证据链，让工程师知道是哪几条证据支撑的，而不是一个黑盒数字。

### 3.2 收敛判据：从单一阈值改成置信度 + 风险双轨

现状 `check_convergence`：

```python
if top1 >= 0.65: return True      # 绝对阈值
if top1 - top2 >= 0.30: ...       # 区分度
if round >= 3 and top1 >= 0.60:   # 轮次兜底
```

问题：**没有风险维度**。在研发/质量域，一条"可能导致批量召回"的结论和一条"内饰异响"的结论，显然不该用同一个阈值。

**改法：双轨判据**

```
收敛 = 置信度达标 AND 风险已评估

风险分 = f(根因严重度, 涉及车量, 是否安全相关, 是否量产车)
  · 高风险 → 阈值上调到 0.85,且【强制转人工】,AI 不出结论
  · 中风险 → 阈值 0.75,结论标注"建议工程师复核"
  · 低风险 → 阈值 0.65,可直接输出
```

### 3.3 追问策略：从 LLM 自由发挥改成信息增益最大

现状 `node_ask_details` 是把候选根因列表丢给 LLM，让它"问能区分 top 候选的问题"。问题：**LLM 不一定问在刀刃上**，而且可能反复问同一维度。

**改法：计算信息增益，主动挑问题**

对每个候选现象，计算"如果用户回答是/否，能减少多少候选集的不确定性"：

```
信息增益(现象p) = H(候选集) - [P(是)·H(候选集|是) + P(否)·H(候选集|否)]
```

挑信息增益最大的 1-2 个现象去问。**这个纯算法实现，不用调 LLM，还能讲"我用量化方法替代了 LLM 自由发挥"**。

同时**硬性禁止重复问**：维护 `asked_phenomena` 集合，已经问过的维度不再进入候选（现在只在 prompt 里写"不要重复问"，靠 LLM 自觉）。

### 3.4 并行化与超时

现状 `graph_queries.py` 用的是同步 Neo4j driver：

```python
def query_causes_by_phenomena(...):     # 同步
    with driver.session() as session:   # 阻塞
```

在 async 图里会**阻塞事件循环**。生产改法：

```python
async def query_causes_by_phenomena(...):
    async with driver.session() as session:
        result = await session.run(...)
```

同时 **Neo4j 图查询（`query_causes_by_phenomena`）和 PG 现象匹配（`match_phenomena_by_names`）是串行依赖的**——前者需要后者的结果做输入，**不能并行**。能并行的是 `enrich_cause_details` 内部的四个扩展查询（`query_dtc_by_relationship` / `query_located_in` / `query_co_occurs_with` 等，都在 `graph_queries.py`，彼此独立），那里可以 `asyncio.gather`。

**注意 `graph_queries.py` 里 5 个函数全是同步的**（`query_causes_by_phenomena`、`enrich_cause_details`、`query_dtc_by_relationship`、`query_located_in`、`query_co_occurs_with`），全部要改成 async。

再叠加**分层超时**：

| 环节 | 超时 | 降级策略 |
|---|---|---|
| LLM 调用 | 30s（现有） | 重试 1 次 → 降级到规则匹配 |
| Neo4j 查询 | 2s | 超时则只用 PG + 向量召回结果 |
| 整体一轮 | 60s | 返回"正在分析"占位，转异步 |

## 4. Issue 闭环：这套方案的核心

"问题单闭环"是场景定位，也是**最能在面试里区别于"我做了个聊天机器人"的部分**。

### 4.1 问题单模型扩展（修正：比预想的好）

**已有字段**（不用加）：`issue_no`、`title`、`description`、`source`、`business_line`、`severity`、`status`、`model_code`（车型代号）、`sw_version`（软件版本）、`vin`（脱敏）、`dtc_snapshot`、`reporter_id`、`owner_domain_id`、`external_ref`，并已有 `status`、`(business_line, model_code)`、`owner_domain_id` 三个索引。

**真正要补的**：

```python
platform: str | None            # 平台（MQB/MEB/...）← model_code 不足以做跨车型迁移
batch_no: str | None            # 生产批次 ← 批次性问题的判定依据
hw_version: str | None          # 硬件版本（已有 sw_version，缺 hw）
mileage_km: int | None          # 里程 ← 磨损类故障的时间维度
occurrence_stage: str           # 试制/量产/售后 ← 判定问题性质
safety_related: bool            # 是否安全相关 ← 高风险门禁的判据
repeat_count: int               # 重复报障次数 ← 判重收敛后的结果
affected_vehicles: int | None   # 涉及车量 ← 质量统计核心指标
canonical_issue_id: int | None  # 指向合并后的主单 ← 判重收敛
sla_deadline: datetime | None   # 按 severity 自动设 SLA
```

**为什么 `platform` 和 `batch_no` 是关键**：只有 `model_code` 时你只能回答"这个车型报了什么"，有了 `platform` 才能回答"**同平台其他车型是不是也这样**"（跨车型知识迁移），有了 `batch_no` 才能回答"**是不是某个批次的问题**"（质量根因定位）。这两问恰是研发质量域的核心。

**为什么要有 `canonical_issue_id`**：10 个车主报同一故障，如果建 10 张单，质量统计会把 1 个批次性问题看成 10 个孤立问题。判重命中后不是丢弃新单，而是挂在主单上（`repeat_count += 1`）。

### 4.2 闭环流程

```
用户报障
   ↓
分诊 (多轮) ──→ 给出候选根因 + 证据链 + 置信度
   ↓
【风险门禁】 ← 高风险直接转人工,AI 不出结论
   ↓
生成 issue_draft (草稿,不是真建单)
   ↓
★ 人工确认 ← 生产必备:AI 不能自动建单
   ↓
调 ALM API 建单 (call_create_issue)
   ↓
工程师跟进 → 标记根因是否准确
   ↓
【反馈回流】
   ├─ 采纳 → 图谱 INDICATES 权重 +5% (现有 feedback_loop)
   ├─ 修正 → 记录正确根因,进入误诊样本集
   └─ 否决 → 权重衰减,连续 N 次否决则停用该路径
```

**★ 关键设计：AI 只出草稿，人工确认才建单。** 这是生产级的硬性边界——
- AI 自动建单 = 污染 ALM 数据（一线最痛恨这个）
- 草稿 + 一键确认 = 既省了人工填写，又保留了人的决策权

这个点在面试里非常加分：**能主动说出"AI 不该做什么"，比说"AI 能做什么"更显成熟。**

### 4.3 反馈闭环的数据结构（修正：后端三段已齐）

现有 `feedback_loop.py` **实现了三段，但只有两段接上了**：

| 段 | 触发 | 动作 | 现有实现 |
|---|---|---|---|
| 正向增强 | 结论被采纳 | `MERGE (rc)-[r:INDICATES]->(ph)`，已有关系 ×1.05（上限 1.0），新关系从 0.3 起 | `reinforce_graph_on_adopted()` ✅ 已接（feedback 路由） |
| 历史复用 | 新故障匹配到已闭环单 | 查 `ai_triage_results` 返回历史结论并格式化 | ⚠️ 函数已实现，**未接入 graph** —— `search_historical_cases()` / `format_historical_cases()` 全仓库无调用点，triage graph 里没有这一步 |
| **误诊衰减** | 诊断被否决 | 权重 ×0.6；连续 3 次否决或权重 < 0.1 时 `DELETE` 关系 | `weaken_graph_on_rejected()` ✅ 已接（feedback 路由） |

★ 另注：`ai_triage_results` 目前**没有 business_line / tenant 列**，所以"按业务线复用历史结论"连数据基础都还不具备 —— 接入前要先补列并在写入时落值。

写入侧入口：`POST /triage/feedback`（`api/routers/triage.py:119`）。

**真正的缺口在三处**：

1. **增强/衰减不对称**：采纳 ×1.05，否决 ×0.8。一次否决 ≈ 抵 4.5 次采纳；且删除阈值设在 0.1 意味着从 1.0 跌到 0.1 需要**连续 11 次否决**。长期看图谱会漂向"只增不减"。建议衰减收紧到 ×0.6 并记录连续否决次数
2. **没有 deprecated 中间态**：只有"< 0.1 就删关系"这一个硬切断。生产上应该先标记 deprecated（保留关系供审计），观察期后再物理删除
3. **误诊样本没沉淀**：否决记录只用来调权重，没有存成**评测集样本**。这是把线上反馈变成 L1/L2 评测数据的最短路径，白白浪费了（**P1 已把它列为评测集的种子来源**）

**★ 更值得做的：反馈结果从"调权重"升级为"改答案"**

现在的三段全是**调图谱权重**，但研发场景里最高频的反馈其实是——**分诊错了，正确根因是另一个**。这类反馈应该同时：

```
工程师标记"结论错误，真实根因是 RC-xxx"
   ↓
① 调权重（现有）：原根因 ×0.8，正确根因的 现象→根因 关联 MERGE 并提权
② 沉淀样本（缺）：写入误诊样本集，进评测集 L2/L3
③ 触发告警（缺）：同一 现象组合 连续误诊 ≥3 次 → 告警提示知识库需人工复核
```

第①条现在**完全没做**——`weaken_graph_on_rejected` 只降了错误根因的权重，没有把正确根因加进去。这意味着系统**不会从误诊中学会正确答案**，只会变得"更不确定"。这是反馈闭环里最实质的一个洞。

### 4.4 去重与合并（修正：已有双门槛，只需扩展维度）

现有 `dedup/matcher.py` **不是单纯文本相似度**，已经实现了**双门槛**：

```
门槛一：向量相似（Milvus embedding 余弦）≥ 0.88
门槛二：结构化精确匹配（DTC 集合，_split_dtc）
两者都过才算重复
```

这个设计比纯向量检索好，值得在面试里讲。要补的是**维度扩展**：

```
判重分 = 现有双门槛（向量 ≥0.88 AND DTC 交集）
       + 同 model_code / 同 platform   ← 新增：跨车型迁移
       + sw_version 接近度             ← 新增：版本相关故障
       + 时间窗口接近度                ← 新增：批次性问题
```

命中后**不丢弃新单**，而是挂到主单上——需要 `AlmIssue.canonical_issue_id` 字段（§4.1）。这是当前模型里唯一缺的、且对质量统计至关重要的字段。

## 5. 研发域特有：变更影响分析增强

现有 `impact/review.py` 比较薄。研发质量域里，**"这个变更会不会引入新故障"** 是高频刚需。

```
输入：CR/变更单
   ↓
解析变更涉及的配置项/ECU/软件模块
   ↓
在图谱里查：这些模块历史上有哪些故障？
   ↓
交叉查询：本次变更是否触碰到历史故障的高发区域？
   ↓
输出：
  · 基线冲突检查
  · 配置项依赖冲突
  · ★ 历史故障回溯：改了 X 模块，历史上 X 相关故障有哪些
  · 在途重复变更
  · 风险等级 + 建议
```

**这个功能的价值**：把 `RootCause` 图谱从"诊断用"延伸到"变更评审用"，同一份知识资产两个场景复用。面试里讲这个能体现**架构复用思维**。

## 6. 质量与安全（面试重点，务必准备）

### 6.1 责任边界：AI 能做什么、不能做什么

| 动作 | AI 权限 | 依据 |
|---|---|---|
| 提取现象、归一化 | ✅ 自动 | 低风险，可回滚 |
| 给出候选根因排序 | ✅ 自动 | 明确标注"候选"，非结论 |
| 生成问题单草稿 | ✅ 自动 | 不写库，等确认 |
| **正式建单/改单** | ⚠️ **需人工确认** | 污染 ALM 数据不可逆 |
| **高风险故障出结论** | ❌ **强制转人工** | 安全/批量风险 |
| 修改图谱权重 | ✅ 自动（有界） | 单次 ≤5%，可追溯 |
| **停用某条根因** | ⚠️ 连续 3 次误诊后自动 + 告警 | 影响面大 |

### 6.2 幻觉与事实性控制

汽车领域的幻觉代价很高（"这个 DTC 表示电池热失控"——如果错了，可能导致误判）。控制手段：

1. **现象名白名单约束**：现在 prompt 里写"不要编造新现象名"，靠 LLM 自觉。生产要**代码级校验**——LLM 输出的现象名不在词汇表里就丢弃（`phenomenon_normalizer.py` 已有基础，要加严格模式）
2. **DTC 码格式 + 存在性校验**：LLM 抽出的 DTC 码要过正则 + 查库确认存在，否则丢弃
3. **根因结论必须可溯源**：结论里的每个根因必须来自图谱查询结果，**不允许 LLM 自由生成根因名**
4. **拒绝回答机制**：信息不足时明确说"无法判断"，而不是硬猜（现在 `node_conclude` 的无结果分支已有雏形）

**第 3 条是硬约束**：`node_conclude` 的 `primary_cause_code` 应该来自 `candidate_causes[0].code`（来自图谱），绝不让 LLM 生成。现在的代码是对的，要在方案里明确这是**设计原则**，别在重构中破坏。

### 6.3 数据安全

- **VIN / 车主信息**：`utils/mask.py` 已有脱敏，要确保**在进 LLM 之前**就脱敏（现在是在哪一层？要确认）。生产原则：**原始数据不出内网、不进第三方 LLM**
- **工程师知识**：内部分析结论属于商业机密，不能进入会训练的外部模型
- **审计日志**：每次诊断的输入/输出/证据链/采纳结果要留痕，满足质量追溯（IATF 16949 要求问题追溯）

### 6.4 可观测

每轮诊断要打出结构化的 trace：

```json
{
  "trace_id": "...",
  "session_id": "...",
  "round": 2,
  "nlp": {"extracted": ["车机黑屏"], "dropped_by_whitelist": [], "llm_latency_ms": 820},
  "retrieval": {"graph_hits": 6, "vector_hits": 4, "fused": 5, "latency_ms": 95},
  "confidence": {"top1": 0.68, "evidence": [{"type":"dtc","code":"U0100","weight":1.0}], "prior": 0.3},
  "decision": {"converged": true, "risk": "low", "threshold": 0.65},
  "cost": {"prompt_tokens": 3200, "completion_tokens": 210}
}
```

**为什么要有**：线上有人投诉"AI 说错了"，你得能回答**错在哪一环**——是现象抽错了？检索没召回？还是置信度算错了？没有 trace 就只能干瞪眼。

## 7. 评测体系

**没有评测集的 agent 项目，面试官一问就露馅。** 这是当前最大的空白。

### 7.1 分层评测

| 层 | 测什么 | 怎么测 | 样本量 |
|---|---|---|---|
| L1 现象提取 | 口语 → 现象名准确率 | 标注集，precision/recall | 200 条 |
| L2 检索 | 现象组合 → 正确根因是否在 Top5 | Recall@5 | 200 条 |
| L3 排序 | 正确根因是否在 Top1 | Top1 命中率 | 200 条 |
| L4 收敛 | 是否在合理轮次收敛 | 平均轮次、收敛率 | 100 会话 |
| L5 端到端 | 结论是否被工程师采纳 | 采纳率（人工标注） | 50 会话 |

### 7.2 数据集怎么来（练手项目的现实做法）

- **冷启动**：从 ALM 历史问题单反向构造——已闭环的单，其「现象描述 → 最终根因」就是天然标注
- **合成**：用 LLM 把标准现象名"翻译"成各种口语说法，扩充 L1 样本
- **对抗**：故意构造边界样本（现象模糊、多故障并发、描述极短）

### 7.3 回归门禁

改 prompt / 改权重 / 换模型后，**必须跑评测集**，关键指标不降才允许合并。这是**把"调 prompt"从玄学变成工程**的关键，面试里讲出来很有说服力。

## 8. 缺陷与风险（主动说出来，面试加分）

| 风险 | 说明 | 缓解 |
|---|---|---|
| **图谱冷启动** | 新车型没有历史数据，图查询召回为 0 | 用同平台车型迁移 + 通用故障模板兜底；明确告知"新车型数据不足" |
| **知识老化** | 老问题已修复但仍被召回 → 误诊 | 时效衰减（半衰期 180 天）+ 软件版本过滤 |
| **反馈闭环的马太效应** | 权重 +5% 会让头部根因越来越强，长尾永远出不来 | 权重上限 + 探索机制（保留一定概率给低权重候选） |
| **LLM 成本** | 研发场景对话长、轮次多 | 分层模型：抽取用便宜模型，结论生成用好模型；缓存词汇表 |
| **多故障并发** | 一辆车同时有 3 个故障，现象互相干扰 | 当前状态是单一 `confirmed_phenomena`，多故障场景要支持"分叉诊断"，这是**明确的能力边界** |
| **无逃生口** | 分诊中切不出去（见 §1） | 本次方案的核心修复项 |

**"多故障并发"和"图谱冷启动"这两条要主动讲**——能说出系统的能力边界在哪，比声称什么都能做可信得多。

## 10. 面试速查：这套方案的核心论点

**如果只有 3 分钟，讲这四点：**

1. **架构上**：从 agent-as-tool 改成单图 + Supervisor 每轮在场，解决了多轮流程"切不出去"的问题。这是个**模式错配**的典型案例——单轮工具模式套多轮有状态需求，必然要打补丁。

2. **可信度上**：置信度从硬编码加法改成证据分级 + Noisy-OR 融合 + 贝叶斯先验，每一分都能溯源到具体证据。汽车领域幻觉代价高，所以现象名、DTC 码、根因名都有代码级白名单校验，**LLM 不能自由生成根因**。

3. **闭环上**：AI 只出问题单草稿，人工确认才建单——**能说清"AI 不该做什么"**。反馈后端三段已实现（提升 ×1.05 / 历史复用 / 衰减 ×0.8），**下一步是把反馈从"调权重"升级为"改答案"**——现在误诊时只降错误根因权重，没把正确根因写回图谱，系统学不会正确答案。这是我在自己项目里找到的最实质的一个洞。

4. **工程上**：有分层评测集（L1-L5）+ CI 回归门禁，把"调 prompt"从玄学变成工程。有全链路 trace，线上答错能定位到具体环节。

**被追问时的弹药：**

- "为什么不用 handoff？" → 单图改动更渐进，现有 triage 图能原样挂进来；handoff 更适合多个平级 agent 互相转交的场景
- "置信度公式怎么定的？" → 权重来自证据等级定义（DTC 是客观测量=1.0，口述=0.7，推断=0.2），融合用 Noisy-OR 保证不会超 1，先验用历史采纳率
- "怎么防止图谱越来越偏？" → 权重有上限 1.0，误诊衰减（现为 ×0.8，建议收紧到 ×0.6）比采纳 ×1.05 激进，配合连续误诊计数
- "这个系统什么做不到？" → 多故障并发（当前是单一现象集）、新车型冷启动（图召回为 0）、需要实车测量的诊断（只能给方向不能给数值）

**★ 主动展示代码级发现（比讲架构更能证明你真的读过项目）：**

- `utils/mask.py` 三个脱敏函数**零调用点**——写了没接线，这是合规硬伤
- `graph_rag.py:51` 的 NL2Cypher Schema 把 INDICATES 写成 `(Phenomenon)->(RootCause)`，而其余 4 处（`graph_queries.py`、`feedback_loop.py`）都是 `(RootCause)->(Phenomenon)`，**同一份图两个方向**，NL2Cypher 会命中不到
- `weaken_graph_on_rejected` 只降错误根因权重、**不写入正确根因**——反馈闭环里最实质的洞
